Hello Docker World

⏱️ 10 mins 📚 Container Basics
Beginner
Objective

Pull your first Docker image, run a container, and understand the basic container lifecycle (run, stop, remove).

Steps
1

Pull the official Nginx image from Docker Hub:

$ docker pull nginx:alpine
2

Run the container in detached mode with port mapping:

$ docker run -d -p 8080:80 --name my-nginx nginx:alpine
3

Verify the container is running and access it in browser:

$ docker ps
$ curl http://localhost:8080
4

View container logs, then stop and remove the container:

$ docker logs my-nginx
$ docker stop my-nginx
$ docker rm my-nginx

✅ Expected Outcome

  • Nginx welcome page visible at http://localhost:8080
  • Container appears in docker ps output
  • Container successfully stopped and removed

Build Your First Image

⏱️ 15 mins 📚 Dockerfile Basics
Beginner
Objective

Create a simple Dockerfile for a static HTML website and build your first custom Docker image.

Steps
1

Create a project folder and an index.html file:

$ mkdir my-website && cd my-website
$ echo "<h1>Hello from Docker!</h1>" > index.html
2

Create a Dockerfile with the following content:

FROM nginx:alpine
COPY index.html /usr/share/nginx/html/
EXPOSE 80
3

Build the image with a custom tag:

$ docker build -t my-website:v1 .
4

Run a container from your new image:

$ docker run -d -p 8080:80 my-website:v1

✅ Expected Outcome

Your custom HTML page displays "Hello from Docker!" at http://localhost:8080

🎁 Bonus Challenge

Modify the HTML file, rebuild as my-website:v2, and run both versions on different ports (8080 and 8081).

Container Exploration

⏱️ 15 mins 📚 Container Internals
Beginner
Objective

Learn to interact with running containers using exec, inspect their details, and understand container isolation.

Steps
1

Start an Ubuntu container in interactive mode:

$ docker run -it --name explorer ubuntu:22.04 bash
2

Inside the container, explore the filesystem and create a file:

# Inside container
root@container# ls /
root@container# cat /etc/os-release
root@container# echo "I was here" > /tmp/myfile.txt
root@container# exit
3

Restart the container and check if the file persists:

$ docker start explorer
$ docker exec -it explorer cat /tmp/myfile.txt
4

Inspect container details:

$ docker inspect explorer --format '{{.NetworkSettings.IPAddress}}'
$ docker stats explorer --no-stream

✅ Expected Outcome

  • File persists after container restart (but lost if container is removed)
  • Container has its own IP address and isolated filesystem

Persistent Data with Volumes

⏱️ 20 mins 📚 Data Persistence
Intermediate
Objective

Use Docker volumes to persist database data beyond container lifecycle. Demonstrate data survives container removal.

Steps
1

Create a named volume for PostgreSQL data:

$ docker volume create pgdata
$ docker volume ls
2

Run PostgreSQL with the volume attached:

$ docker run -d --name mydb \
  -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data \
  postgres:15-alpine
3

Create a database and insert data:

$ docker exec -it mydb psql -U postgres

# In psql:
CREATE DATABASE workshop;
\c workshop
CREATE TABLE users (id SERIAL, name VARCHAR(50));
INSERT INTO users (name) VALUES ('Alice'), ('Bob');
SELECT * FROM users;
\q
4

Remove the container and create a new one with the same volume:

$ docker rm -f mydb
$ docker run -d --name mydb2 \
  -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data \
  postgres:15-alpine
5

Verify data persisted:

$ docker exec -it mydb2 psql -U postgres -d workshop -c "SELECT * FROM users;"

✅ Expected Outcome

Data (Alice, Bob) persists even after container removal because it's stored in the volume.

Container Networking

⏱️ 20 mins 📚 Docker Networks
Intermediate
Objective

Create a custom bridge network and enable container-to-container communication using container names as hostnames.

Steps
1

Create a custom bridge network:

$ docker network create mynetwork
$ docker network ls
2

Run a Redis server on the custom network:

$ docker run -d --name redis-server \
  --network mynetwork \
  redis:alpine
3

Run a client container on the same network and connect to Redis:

$ docker run -it --rm --network mynetwork redis:alpine redis-cli -h redis-server

# In redis-cli:
SET greeting "Hello from Docker networking!"
GET greeting
exit
4

Inspect the network to see connected containers:

$ docker network inspect mynetwork

✅ Expected Outcome

  • Client container can reach Redis using hostname "redis-server"
  • Data can be stored and retrieved via Redis
  • Network inspection shows both containers

💡 Key Concept

Custom bridge networks provide automatic DNS resolution. Containers can reach each other by name instead of IP addresses.

Docker Compose - Multi-Container App

⏱️ 25 mins 📚 Orchestration
Intermediate
Objective

Use Docker Compose to define and run a multi-container application (WordPress + MySQL) with a single command.

Steps
1

Create a project directory and docker-compose.yml file:

$ mkdir wordpress-app && cd wordpress-app
2

Create docker-compose.yml with the following content:

version: '3.8' services: db: image: mysql:8.0 environment: MYSQL_ROOT_PASSWORD: rootpass MYSQL_DATABASE: wordpress MYSQL_USER: wpuser MYSQL_PASSWORD: wppass volumes: - db_data:/var/lib/mysql wordpress: image: wordpress:latest depends_on: - db ports: - "8080:80" environment: WORDPRESS_DB_HOST: db:3306 WORDPRESS_DB_USER: wpuser WORDPRESS_DB_PASSWORD: wppass WORDPRESS_DB_NAME: wordpress volumes: db_data:
3

Start all services:

$ docker compose up -d
$ docker compose ps
4

Access WordPress at http://localhost:8080 and complete setup

5

View logs and cleanup:

$ docker compose logs -f # Ctrl+C to exit
$ docker compose down -v # -v removes volumes

✅ Expected Outcome

  • WordPress installation wizard appears at localhost:8080
  • MySQL and WordPress containers running and connected
  • All resources cleaned up with single command

Multi-Stage Build Optimization

⏱️ 25 mins 📚 Image Optimization
Advanced
Objective

Build a Go application using multi-stage builds to create a minimal production image (from ~800MB to ~10MB).

Steps
1

Create a simple Go application (main.go):

package main import ( "fmt" "net/http" ) func main() { http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) { fmt.Fprintf(w, "Hello from optimized Docker image!") }) http.ListenAndServe(":8080", nil) }
2

First, build with a standard Dockerfile (single stage):

FROM golang:1.21 WORKDIR /app COPY main.go . RUN go build -o server main.go CMD ["./server"]
$ docker build -t go-app:single .
$ docker images go-app:single # ~800MB
3

Now create a multi-stage Dockerfile:

# Build stage FROM golang:1.21-alpine AS builder WORKDIR /app COPY main.go . RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o server main.go # Production stage FROM scratch COPY --from=builder /app/server /server EXPOSE 8080 CMD ["/server"]
4

Build and compare sizes:

$ docker build -t go-app:multi .
$ docker images | grep go-app

✅ Expected Outcome

REPOSITORY TAG SIZE
go-app single 814MB
go-app multi 6.5MB

~99% reduction in image size!

Container Health Checks & Restart Policies

⏱️ 20 mins 📚 Production Readiness
Advanced
Objective

Implement health checks in containers and configure restart policies for automatic recovery from failures.

Steps
1

Create a Dockerfile with a health check:

FROM nginx:alpine HEALTHCHECK --interval=10s --timeout=3s --retries=3 \ CMD wget -q --spider http://localhost/ || exit 1 EXPOSE 80
2

Build and run with restart policy:

$ docker build -t healthy-nginx .
$ docker run -d --name web \
  --restart unless-stopped \
  -p 8080:80 healthy-nginx
3

Monitor health status:

$ docker ps # Check STATUS column for (healthy)
$ docker inspect web --format '{{.State.Health.Status}}'
4

Simulate failure and observe restart:

$ docker exec web nginx -s stop
$ docker ps # Container restarts automatically

💡 Restart Policies

  • no - Never restart (default)
  • on-failure - Restart only on non-zero exit
  • always - Always restart
  • unless-stopped - Always, except manual stop

Debug a Failing Container

⏱️ 20 mins 📚 Troubleshooting
Advanced
Objective

Practice debugging techniques for containers that crash or fail to start. Learn to use logs, exec, and inspect for troubleshooting.

Steps
1

Create a "broken" container that exits immediately:

$ docker run -d --name broken alpine sh -c "exit 1"
2

Use debugging commands to investigate:

# Check container status
$ docker ps -a

# View logs
$ docker logs broken

# Inspect exit code
$ docker inspect broken --format '{{.State.ExitCode}}'

# Check why it stopped
$ docker inspect broken --format '{{.State.Error}}'
3

Debug by overriding the entrypoint:

# Start fresh container with shell
$ docker run -it --entrypoint /bin/sh alpine

# Or copy files from failed container
$ docker cp broken:/etc/alpine-release ./
4

Use docker events for real-time monitoring:

$ docker events --filter 'container=broken'

✅ Debugging Toolkit

  • docker logs - View stdout/stderr
  • docker inspect - Full container metadata
  • docker exec - Run commands in running container
  • docker cp - Copy files in/out
  • docker events - Real-time event stream

Build a Full-Stack Application

⏱️ 45 mins 📚 Capstone Project
Challenge
Objective

Build and deploy a complete 3-tier application with frontend (Nginx), backend (Node.js/Python), and database (PostgreSQL/MongoDB) using Docker Compose.

Requirements
✓

Frontend: Nginx serving static files, proxying API requests to backend

✓

Backend: REST API (Node.js Express or Python Flask) with database connection

✓

Database: PostgreSQL or MongoDB with persistent volume

✓

Networking: Custom network for internal communication

✓

Health Checks: Implement for all services

✓

Environment: Use .env file for configuration

Sample Structure
fullstack-app/
├── docker-compose.yml
├── .env
├── frontend/
│ ├── Dockerfile
│ ├── nginx.conf
│ └── index.html
├── backend/
│ ├── Dockerfile
│ ├── package.json
│ └── server.js
└── database/
└── init.sql

🏆 Bonus Points

  • Use multi-stage builds for backend
  • Implement hot-reload for development
  • Add Redis for caching layer
  • Configure resource limits (CPU/memory)
  • Add logging aggregation

✅ Success Criteria

  • All services start with docker compose up -d
  • Frontend accessible at http://localhost
  • API responds at http://localhost/api
  • Data persists after docker compose down && docker compose up
  • Health checks pass for all services
